[[CORE-FN-007]]
== CORE-FN-007 Opt In to Monotonic Timestamps (CORE-93)

Date:: 2026-11-10
Context::
* `SystemTimeProvider` can return decreasing timestamps under concurrent calls or a backward wall-clock adjustment.
* Existing direct users and Chronicle Bytes uniqueness providers should retain its lightweight algorithm.
Decision Statement::
* Add `MonotonicTimeProvider`, with a volatile clock delta and a shared atomic maximum for nanoseconds; microseconds derive from that result.
* Select it through `SystemTimeProvider.CLOCK` when `Jvm.getBoolean("chronicle.time.monotonic")` is true at class initialisation. The absent or false property retains `SystemTimeProvider` in 2026.x. The monotonic provider may become the default in 2027.x.
* Keep the shared clock mutable for test overrides and leave direct `SystemTimeProvider.INSTANCE` calls unchanged.
Rationale for Decision::
* The atomic maximum prevents older estimates from reversing ordered calls, including calls on different threads.
* Explicit opt-in keeps the shared atomic update off existing default call paths.
Impact & Consequences::
* Timestamps are non-decreasing, not unique. Overlapping calls are ordered by their atomic updates rather than their returns.
* Clock rollback can freeze the result ahead of wall time until the estimate catches up; milliseconds still read wall time directly.
* Controlled clock-step and cross-thread handoff tests complement live-clock contention tests. Worker failure, startup failure and interruption must leave no owned workers running.

[[CORE-DOC-001]]
== CORE-DOC-001 Adopt Nine-Box Requirement & Decision Taxonomy

Context::
* Numerous Chronicle projects expressed difficulty tracing requirements to code and to ADRs.
* A single, cross-project taxonomy is required for tooling (link-checks, changelogs).
Decision Statement::
* Chronicle Core **adopts** the Nine-Box tag set (`FN`, `NF-P`, `NF-S`, `NF-O`, `TEST`, `DOC`, `OPS`, `UX`, `RISK`) for all requirement and decision identifiers.
Alternatives Considered::
* *Free-form tags* - flexible but unsearchable; high risk of duplication.
* *SAFe epic/capability IDs* - too coarse for low-level library work.
Rationale for Decision::
* Provides immediate traceability across projects with minimal ceremony.
* Aligns with company-wide governance already approved under `ALL-DOC-100`.
Impact & Consequences::
* Existing requirement IDs were renumbered (see link:functional-requirements.adoc[Functional Requirements]).
* Tooling scripts must update regexes to recognise new tag set.
Notes/Links::
* link:functional-requirements.adoc[Functional Requirements Spec]

[[CORE-OPS-002]]
== CORE-OPS-002 Enforce Deterministic Resource Lifecycle via `AbstractCloseable` & `ReferenceCounted`

Context::
* Off-heap memory and mmap handles are invisible to the JVM GC.
* Production leaks previously caused kernel `ENFILE` (too many open files) errors.
Decision Statement::
* All classes that manage native resources **MUST** extend `AbstractCloseable`
*and* implement `ReferenceCounted` when those resources are shareable.
Alternatives Considered::
* *Rely on `finalize()`* - deprecated in JDK 18; unpredictable latency.
* *Cleaner API* - safer, but incurs allocation-heavy reachability fences.
Rationale for Decision::
* `AbstractCloseable` already proven in Queue/Bytes with micros-level overhead.
* Reference counting guarantees orderly teardown in multi-thread/process use cases.
Impact & Consequences::
* API surface grows (extra methods), but IDE templates mitigate ergonomic cost.
* Library will throw `ClosedIllegalStateException` sooner, surfacing bugs earlier.

[[CORE-RISK-003]]
== CORE-RISK-003 Guard Native-Memory Mapping with Directory Whitelist

Context::
* FinReg audit highlighted potential breakout via malicious path traversal in `OS.map(FileChannel,...)`.
Decision Statement::
* Introduce optional system property `chronicle.core.mmap.allowedDirs`
(comma-separated list).
When set, **any** attempt to memory-map a file outside these directories fails fast with a `SecurityException`.
Alternatives Considered::
* *Do nothing* - cheaper but fails compliance for tier-1 banks.
* *Java SecurityManager checks* - SecurityManager removed in JDK 18.
Rationale for Decision::
* Simple, zero-allocation check; satisfies audit without penalising normal users (property unset = current behaviour).
Impact & Consequences::
* Deployment pipelines must populate the property in regulated environments.
* Adds a branch in `OS.java`; micro-benchmark shows < 1 ns overhead.
Notes/Links::
* Jira SEC-417 link to internal audit ticket.
* link:functional-requirements.adoc#CORE-FN-006[CORE-FN-006]

[[CORE-NF-O-004]]
== CORE-NF-O-004 Background Resource Releaser Thread (Opt-In)

Context::
* Large queues (> 64 GiB) experience 5-10 ms stalls during `munmap`.
* Trading paths are sensitive to > 100 micros hiccups.
Decision Statement::
* Provide `BackgroundResourceReleaser` singleton.
When system property `chronicle.core.backgroundRelease=true` is set,
`AbstractCloseable.performClose()` submits the heavy deallocation to this low-priority thread, returning immediately.
Alternatives Considered::
* *Always release synchronously* - simplest, but violates latency SLOs.
* *Thread-pool per caller* - avoids single bottleneck but over-complex.
Rationale for Decision::
* Keeps hot path predictable; opt-in preserves zero-thread baseline for most users.
Impact & Consequences::
* One extra daemon thread when enabled; must be listed in operations run-books.
* Resource leak detector must join on the thread before JVM exit in tests.
Notes/Links::
* Performance numbers in attached JMH `munmap-benchmark.md`.
* link:functional-requirements.adoc#CORE-FN-030[CORE-FN-030]

[[CORE-FN-005]]
== CORE-FN-005 ChronicleInit for Pre/Post Application Hooks

Context::
* Initialisation steps for some applications must run before Chronicle reads any system properties.
* Other hooks must execute after `Jvm` static initialisation completes.
Decision Statement::
* Provide `ChronicleInit` to load and run classes specified by
`chronicle.init.runnable` and `chronicle.postinit.runnable` system properties.
* Support `ChronicleInitRunnable` implementations discovered via `ServiceLoader`.
Alternatives Considered::
* *Static blocks in `Jvm`* - simple but hard to extend by user code.
* *External bootstrap scripts* - violate embedability and complicate deployment.
Rationale for Decision::
* Gives applications controlled extension points without requiring code changes.
Impact & Consequences::
* Hooks may modify system properties or start services during startup.
* Misconfigured hooks could delay application launch or throw exceptions.
Notes/Links::
* link:functional-requirements.adoc#CORE-FN-015[CORE-FN-015]

[[CORE-FN-419]]
== CORE-FN-419 Retain Volatile Float and Double Accessors

Context::
* Chronicle Bytes exposes volatile float and double operations through its public random-access interfaces.
* ARM requires a fallback when a float or double is not naturally aligned.
* The existing ARM object-offset operations inherited unsafe unaligned platform primitives, and the direct double write omitted its release fence.
Decision Statement::
* Retain the volatile float and double API rather than deprecating it.
* Use the platform volatile primitive for aligned access.
* For misaligned ARM reads, perform the plain bit-preserving read before the acquire fence.
* For misaligned ARM writes, place the release fence before the plain bit-preserving store, ordering prior payload accesses before publication. A fence after both stores cannot establish that ordering.
* Misaligned access can tear and does not provide full volatile semantics. Callers requiring an atomic publication marker must align the value to its natural width.
Alternatives Considered::
* *Deprecate the methods for removal* - avoids maintaining ARM fallbacks but cascades into the Chronicle Bytes public API.
* *Reject every misaligned access* - gives a simpler atomicity rule but removes behaviour already supported by the memory abstraction.
Rationale for Decision::
* The cross-project API usage makes removal a larger compatibility decision than issue #419.
* Explicit ARM fallbacks preserve the existing API while stating the alignment limitation.
Impact & Consequences::
* ARM direct-address, object-offset and null-object paths share the same ordering contract.
* Tests exercise misaligned ordering and raw floating-point representations; successful stress runs do not prove atomicity or replace ARM hardware qualification.
* Concurrent ordering tests stop and join every started worker before releasing native memory, including owner interruption and partial startup failure. Test discovery does not allocate their native storage.
* Temporary ordering diagnostics identify each mode/offset, retain last observed marker bits and acknowledgement values, and preserve worker exceptions alongside a separate post-join memory snapshot. A passing diagnostic build does not establish a product repair; the extra observations can affect compilation and timing.
Notes/Links::
* GitHub issue #419.

[[CORE-TEST-006]]
== CORE-TEST-006 Preserve First-Attempt Unit-Test Failures

Date:: 2026-09-12
Context::
* Automatic Surefire retries can turn an intermittent failure into a successful build.
* Shared CI command lines can request retries with `-Dsurefire.rerunFailingTestsCount`.
Decision Statement::
* Set `rerunFailingTestsCount` to the literal value `0` in the Core Surefire plugin configuration.
* Keep this value independent of Maven properties so command-line retry requests cannot enable automatic reruns.
Rationale for Decision::
* Each test invocation must retain its original outcome for failure triage.
* Bounded, explicitly recorded repeat runs remain useful for investigating intermittent failures.
Impact & Consequences::
* Intermittent unit-test failures remain visible and need investigation.
* This controls Surefire reruns; CI must still treat reported test failures as failures when it uses `maven.test.failure.ignore` to continue to later steps.
Validation::
* Check the effective POM with a non-zero command-line retry count, including the `sonar` and `run-all-tests` profiles.
* Run ordinary and dynamic JUnit tests that fail on their first invocation and would pass on a second invocation.
* With `-Dsurefire.rerunFailingTestsCount=3`, both `test` and direct `surefire:test` must execute each probe once and report failure.
