[[CORE-DOC-001]]
== CORE-DOC-001 Adopt Nine-Box Requirement & Decision Taxonomy

Context::
* Numerous Chronicle projects expressed difficulty tracing requirements to code and to ADRs.
* A single, cross-project taxonomy is required for tooling (link-checks, changelogs).
Decision Statement::
* Chronicle Core **adopts** the Nine-Box tag set (`FN`, `NF-P`, `NF-S`, `NF-O`, `TEST`, `DOC`, `OPS`, `UX`, `RISK`) for all requirement and decision identifiers.
Alternatives Considered::
* *Free-form tags* - flexible but unsearchable; high risk of duplication.
* *SAFe epic/capability IDs* - too coarse for low-level library work.
Rationale for Decision::
* Provides immediate traceability across projects with minimal ceremony.
* Aligns with company-wide governance already approved under `ALL-DOC-100`.
Impact & Consequences::
* Existing requirement IDs were renumbered (see link:functional-requirements.adoc[Functional Requirements]).
* Tooling scripts must update regexes to recognise new tag set.

* link:functional-requirements.adoc[Functional Requirements Spec]

[[CORE-OPS-002]]
== CORE-OPS-002 Enforce Deterministic Resource Lifecycle via `AbstractCloseable` & `ReferenceCounted`

Context::
* Off-heap memory and mmap handles are invisible to the JVM GC.
* Production leaks previously caused kernel `ENFILE` (too many open files) errors.
Decision Statement::
* All classes that manage native resources **MUST** extend `AbstractCloseable`
*and* implement `ReferenceCounted` when those resources are shareable.
Alternatives Considered::
* *Rely on `finalize()`* - deprecated in JDK 18; unpredictable latency.
* *Cleaner API* - safer, but incurs allocation-heavy reachability fences.
Rationale for Decision::
* `AbstractCloseable` already proven in Queue/Bytes with micros-level overhead.
* Reference counting guarantees orderly teardown in multi-thread/process use cases.
Impact & Consequences::
* API surface grows (extra methods), but IDE templates mitigate ergonomic cost.
* Library will throw `ClosedIllegalStateException` sooner, surfacing bugs earlier.

[[CORE-RISK-003]]
== CORE-RISK-003 Guard Native-Memory Mapping with Directory Whitelist

Context::
* FinReg audit highlighted potential breakout via malicious path traversal in `OS.map(FileChannel,...)`.
Decision Statement::
* Introduce optional system property `chronicle.core.mmap.allowedDirs`
(comma-separated list).
When set, **any** attempt to memory-map a file outside these directories fails fast with a `SecurityException`.
Alternatives Considered::
* *Do nothing* - cheaper but fails compliance for tier-1 banks.
* *Java SecurityManager checks* - SecurityManager removed in JDK 18.
Rationale for Decision::
* Simple, zero-allocation check; satisfies audit without penalising normal users (property unset = current behaviour).
Impact & Consequences::
* Deployment pipelines must populate the property in regulated environments.
* Adds a branch in `OS.java`; micro-benchmark shows < 1 ns overhead.
Notes/Links::
* Jira SEC-417 link to internal audit ticket.
* link:functional-requirements.adoc#CORE-FN-006[CORE-FN-006]

[[CORE-NF-O-004]]
== CORE-NF-O-004 Background Resource Releaser Thread (Opt-In)

Context::
* Large queues (> 64 GiB) experience 5-10 ms stalls during `munmap`.
* Trading paths are sensitive to > 100 micros hiccups.
Decision Statement::
* Provide `BackgroundResourceReleaser` singleton.
When system property `chronicle.core.backgroundRelease=true` is set,
`AbstractCloseable.performClose()` submits the heavy deallocation to this low-priority thread, returning immediately.
Alternatives Considered::
* *Always release synchronously* - simplest, but violates latency SLOs.
* *Thread-pool per caller* - avoids single bottleneck but over-complex.
Rationale for Decision::
* Keeps hot path predictable; opt-in preserves zero-thread baseline for most users.
Impact & Consequences::
* One extra daemon thread when enabled; must be listed in operations run-books.
* Resource leak detector must join on the thread before JVM exit in tests.
Notes/Links::
* Performance numbers in attached JMH `munmap-benchmark.md`.
* link:functional-requirements.adoc#CORE-FN-030[CORE-FN-030]

[[CORE-FN-005]]
== CORE-FN-005 ChronicleInit for Pre/Post Application Hooks

Context::
* Initialisation steps for some applications must run before Chronicle reads any system properties.
* Other hooks must execute after `Jvm` static initialisation completes.
Decision Statement::
* Provide `ChronicleInit` to load and run classes specified by
`chronicle.init.runnable` and `chronicle.postinit.runnable` system properties.
* Support `ChronicleInitRunnable` implementations discovered via `ServiceLoader`.
Alternatives Considered::
* *Static blocks in `Jvm`* - simple but hard to extend by user code.
* *External bootstrap scripts* - violate embedability and complicate deployment.
Rationale for Decision::
* Gives applications controlled extension points without requiring code changes.
Impact & Consequences::
* Hooks may modify system properties or start services during startup.
* Misconfigured hooks could delay application launch or throw exceptions.

[[CORE-RISK-331]]
== CORE-RISK-331 Stage Finaliser Replacement Behind a Private Migration

Date:: 2026-08-22
Context::
* Chronicle Core contains two production safety-net finalisers and one finalisation-based test barrier.
* Removing a safety net without a replacement can turn a forgotten close into a descriptor or resource leak.
* Chronicle Core still supports Java 8, where `java.lang.ref.Cleaner` is unavailable.
* A bespoke public cleaner would create a permanent compatibility commitment before its worker, class-loader and registration lifecycle had been proven.
Decision Statement::
* This increment records the inventory and evidence only; it does not introduce a cleaner API or remove a finaliser.
* A migration must keep the reference implementation private and expose only an idempotent cleanup handle.
* The first migration must replace one production finaliser and include a fail-before/pass-after release test under `--finalization=disabled`.
* Queue processing must have deterministic tests. A GC-driven test may supplement them but cannot be the principal correctness test.
* Worker context-class-loader, interruption, termination and registration reachability must be designed before automatic cleanup is enabled.
Alternatives Considered::
* *Publish a Java 8 cleaner before migrating a finaliser* - rejected because it exposes unused API and unresolved lifecycle hazards.
* *Delete the finalisers now* - rejected because that removes leak protection without replacement evidence.
* *Wait without recording evidence* - rejected because the inventory and disabled-finalisation behaviour would remain implicit.
Rationale for Decision::
* A private, concrete migration is reversible and proves resource release before an API commitment is made.
* The current decision separates research from production lifecycle code.
Impact & Consequences::
* Issue #331 remains open.
* Existing finaliser behaviour remains unchanged in this increment.
* The follow-up migration can be validated on current JDKs without waiting for finalisation to be physically removed.

* link:finalisation-migration.adoc[Finalisation migration inventory and evidence]
