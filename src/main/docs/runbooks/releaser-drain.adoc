= Runbook: Draining the Background Resource Releaser
:toc:
:sectnums:
:lang: en-GB
:source-highlighter: rouge

Related requirements: CORE-OPS-005, CORE-FN-030, CORE-FN-039.

== Purpose

Use this runbook when JVM shutdown stalls or leak detectors report pending work because
`BackgroundResourceReleaser` keeps references queued after application code called `close()`.

== Signals and Metrics

* Logs: repeated WARN entries about delayed release or shutdown hanging on `BackgroundResourceReleaser`.
* Threads: dumps show a running `BackgroundResourceReleaser` thread after `Jvm.shutdown()` was invoked.
* Duration: shutdown should complete within 2 seconds (CORE-OPS-005); longer times indicate a problem.

== Preconditions

* Access to JVM logs and the ability to trigger `BackgroundResourceReleaser.dumpQueue()` (via JMX, debugger or an in-app diagnostic endpoint).
* Knowledge of the Chronicle Core version and whether
`-Dchronicle.core.backgroundRelease=true` is set.

== Steps

. *Confirm background release state*
* Inspect JVM flags or log lines for `BackgroundResourceReleaser is enabled`.
* If disabled, fall back to the synchronous leak investigation guide.
. *Dump pending resources*
* Invoke `BackgroundResourceReleaser.dumpQueue()`; capture the class names and `ReferenceOwner`
labels that appear.
* Cross-reference each entry with the owning subsystem (Queue, Bytes, custom component).
. *Collect thread dump*
* Take a thread dump to confirm `BackgroundResourceReleaser` is running and to capture blocking call stacks.
. *Check reference counts*
* For each class in the dump, ensure `ReferenceCounted.refCount()` eventually reaches zero.
Missing `release(owner)` calls are the common failure.
* Enable `-Djvm.resource.tracing=true` temporarily to capture stack traces for offending owners.
. *Force drain before shutdown*
* Call `BackgroundResourceReleaser.closeAll()` (available in tests/utilities) or wait on
`BackgroundResourceReleaser.releasePendingResources()` loops until the queue size is zero.
* In integration tests, call `Jvm.shutdown()` and assert it returns within 2 seconds.
. *Apply fixes*
* Patch the leaking code path to pair every `reserve(owner)` with a `release(owner)`.
* Consider disabling background release temporarily in production (`-Dchronicle.core.backgroundRelease=false`) if the fix cannot be rolled out immediately.

== Verification

* `BackgroundResourceReleaser.dumpQueue()` prints `Queue is empty`.
* Graceful shutdowns (and unit tests) complete without a >2 second delay.
* Resource tracing logs show balanced reserve/release counters for the previously leaking component.
* Coverage: CORE-OPS-005, CORE-FN-039.

== Edge Cases

* Releaser disabled: when `-Dbackground.releaser=false`, leaks are synchronous; follow synchronous leak guidance instead.
* Heavy pending queue: during peak load, draining may take longer; allow a bounded grace period before forcing exit.
* Tracing enabled: reference tracing increases overhead; consider disabling during shutdown investigations if noise is high.

== Rollback

* Revert Chronicle Core to a version without background release if the feature is non-essential.
* Disable the background releaser flag and restart the service to return to synchronous cleanup while the leak is investigated.
