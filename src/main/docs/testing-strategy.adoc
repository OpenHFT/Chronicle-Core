This document outlines the testing approach for Chronicle Core and links tests to the Nine-Box
requirements defined in `functional-requirements.adoc` and `project-requirements.adoc`.
It supports the ISO 9001 design verification checklist and helps reviewers assess coverage for key
behaviours.

== Test Layers

Chronicle Core uses several complementary test layers:

* unit tests in `src/test/java/net/openhft/chronicle/core` for OS and JVM utilities, memory access,
  deterministic resource management, and thread-safety guards (CORE-FN-001..055);
* integration-style tests that exercise combinations of Core APIs used by other Chronicle modules
  (for example Queue, Bytes, Wire, Threads) where appropriate;
* binary-compatibility checks enforced by the `binary-compatibility-enforcer` plugin;
* micro-benchmarks and higher-level harnesses in dependent repositories for performance-sensitive
  requirements that rely on Core primitives.

Where practical, test classes and methods reference requirement IDs (for example `CORE-FN-015`,
`CORE-FN-030`, `CORE-FN-040`) in comments or Javadoc to support traceability.

== Unit Testing Approach

Unit tests focus on:

* OS abstraction: PID, host-name, page size and temp directory helpers (CORE-FN-001..006);
* JVM interaction: system property loading, init hooks, safepoint helpers and exception handling
  (CORE-FN-010..021);
* low-level memory access: read/write, CAS, fences and volatile operations via `Memory` and
  `UnsafeMemory` (CORE-FN-022..029);
* deterministic resource management: lifecycle and reference counting for `AbstractCloseable`,
  `ReferenceCounted` and related types (CORE-FN-030..039, decision `CORE-OPS-002`);
* thread-safety helpers: `SingleThreadedChecked`, `CleaningThreadLocal` and related patterns
  (CORE-FN-040..043);
* low-level utilities: hashing, maths functions, string and enum helpers (CORE-FN-044..055).

Tests are written to avoid non-deterministic timing assumptions and to keep allocations low,
reflecting the performance-sensitive nature of the library.

== Integration and Compatibility Tests

Integration-style tests cover:

* combined usage of Core utilities in scenarios that approximate real consumers (for example
  mapping files and using `Memory` to access them, or combining resource management with
  thread-safety guards);
* behaviour under different JVM versions and operating systems, aligned with compatibility
  requirements documented in `operational-requirements.adoc`;
* binary compatibility of public APIs via the Maven plugin configured in `pom.xml`, which acts as
  an automated check against accidental breaking changes.

Where possible, integration tests reuse production configuration defaults so that changes in
settings (for example system properties or background releaser flags) are exercised in CI.

== Performance and Regression Checks

Performance-related expectations are primarily expressed in terms of:

* avoiding unexpected allocations and synchronisation on hot paths (for example resource tracing,
  logging, thread guards);
* bounding the overhead of optional features such as resource tracing or background releasers;
* enabling higher-level modules to meet their own latency and throughput targets when built on top
  of Core.

Performance is validated using:

* focused unit tests that check for zero allocations in critical methods where feasible;
* micro-benchmarks and scenario tests that live in dedicated benchmark modules or dependent
  repositories (for example Queue and Threads), with results referenced from Core decision and
  requirements documents where appropriate.

== Traceability and Coverage

To improve traceability between requirements, decisions and tests:

* new tests should reference the relevant `CORE-FN-xxx` or `CORE-OPS-xxx` identifiers in comments
  or test names where practical;
* significant bug fixes should include regression tests and, where applicable, a reference back to
  the requirement or decision they reinforce;
* future extensions of the `CORE-NF-P-*` and `CORE-NF-S-*` requirements in the requirements
  catalogue should be accompanied by targeted tests and updates to this strategy.

This document does not attempt to quantify exact coverage percentages; instead it describes the
expected relationships between requirements and tests so that CODEOWNERS and reviewers can assess
whether new changes maintain or improve coverage.

== Running the Test Suite

From the repository root, run:

[source,bash]
----
mvn -q clean verify
----

This command builds all modules, executes unit and integration tests and runs static analysis tools
configured in the Maven build.
Module-specific test runs can be scoped using Maven's `-pl` flag when iterating, but full `verify`
should be executed before releases or pull requests.
